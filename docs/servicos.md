Cópia de todos os arquivos abaixo em `arquivos-da-box/` (mesmo caminho relativo à raiz da box).

## Acesso
- LAN **`192.168.0.4` fixo** (netplan na própria box; o roteador não tem reserva por MAC e o DHCP dele vai de .10 a .254), Tailscale `100.x.y.z` (`pihole-box`). Usuário `mopar` (sudo); root com a mesma senha. Credenciais: `credenciais/rk322x-flash/.env` do mq.
- Rodar coisas: `scripts/box.sh <script.sh>` ou `scripts/box.sh -c '<cmd>'` (cai para o Tailscale sozinho fora de casa).
- **Mandar script por stdin**, nunca aninhar aspas em `plink "sudo sh -c '...'"` (o `$2` do awk quebrou e um `apt full-upgrade` começou antes das travas).
- PowerShell engole argumento vazio (`-pw ""`): para o multitool (senha vazia) usar o plink pelo Git Bash.

## Pi-hole v6 + Unbound (DNS)
- Pi-hole 6.4.3 / FTL 6.7.1 / Web 6.6, instalado com `PIHOLE_SKIP_OS_CHECK=true ... --unattended` e `setupVars.conf` pré-preenchido. Painel `http://192.168.0.4/admin` (senha = a do `mopar`).
- Upstream único: **Unbound `127.0.0.1#5335`** encaminhando por **DoT** (Quad9 `9.9.9.9@853#dns.quad9.net` + Cloudflare `1.1.1.1@853#cloudflare-dns.com`), com `prefetch`, `serve-expired`, DNSSEC. Benchmark que decidiu: recursivo próprio 307 ms mediana com cache vazio (1,5 s pior), encaminhado simples 87 ms, DoT 99 ms; com cache, 0–3 ms em todos. Configs alternativas em `/opt/netlab/unbound/`.
- Unbound no Trixie precisa de `dns-root-data` + `unbound-anchor` (senão `root.key` não existe e o serviço não sobe).
- Porta 53 liberada: `DNSStubListener=no` no resolved; a própria box resolve por `127.0.0.1`.
- **Listas** (841 mil domínios): StevenBlack + HaGeZi **`raw.githubusercontent.com/hagezi/dns-blocklists/main/adblock/pro.txt`** e **`.../adblock/tif.medium.txt`**. O jsDelivr dá **403** e a pasta `domains/` **não existe mais** — o Pi-hole v6 lê o formato Adblock (`||dominio^`).
- Resultado medido: 45/45 domínios de anúncio bloqueados, 60/60 sites normais ok, 3–4 ms do PC de casa, ~660 consultas/s em DDR 660.
- `dns.listeningMode = ALL` **só é seguro com o firewall `dnsguard`** (nftables, tabela própria `inet dnsguard`, serviço `dnsguard`): porta 53 só para `lo`, `tailscale0`, IPv4 privado e IPv6 link-local/ULA. A box tem **IPv6 público da Claro**; sem a trava vira resolvedor aberto.
- Durante a troca da gravity, uma consulta pode vazar por segundos — normal.
- Log de consultas: `pihole-FTL sqlite3 /etc/pihole/pihole-FTL.db "SELECT ... FROM queries ..."` (gravado no disco a cada minuto). `status` 1/4/5/9/10/11 = bloqueado; `reply_type` 1 NODATA, 2 NXDOMAIN, 7 SERVFAIL.

## Roteador da Claro (lido em 14/10, nada alterado)
- Modem/roteador Kaon (MAC `xx:xx:xx:xx:xx:xx`), DOCSIS 3.1, painel Vue em `http://192.168.0.1`. **Há dois campos de isca ocultos antes do usuário/senha reais** (classe `input`); no Playwright usar `input.input[...]` + `focus()` + teclado + Enter (o clique é interceptado pelo título). No Git Bash usar `MSYS_NO_PATHCONV=1` senão `#/rota` vira caminho de arquivo. Roteiro: `scratchpad/pw/rot-nav.js "#/network/dnsv4" ...`.
- **Não tem reserva de IP por MAC.** DHCP entrega `.10`–`.254` (245 CPEs, lease 1 dia); `.2`–`.9` ficam livres para IP fixo configurado **no próprio aparelho** (é assim que o servidor está em `.5`).
- **LAN/DNSv4** (`#/network/dnsv4`): DNS primário/secundário + "Usar esses servidores de DNS" → é onde apontar a casa para o Pi-hole. Hoje vazio (o 8.8.8.8 + Claro vem da WAN).
- **IPv6**: o roteador anuncia os DNS IPv6 da Claro (`2804:14d:1:0:181:213:132:2/.3`) e o DHCPv6 **não tem campo de DNS** → aparelhos com IPv6 podem consultar a Claro por fora do Pi-hole mesmo com o DNSv4 apontado.
- **O DNS IPv6 da Claro fura o Pi-hole na casa toda** (medido 14/10 22:20): o roteador anuncia `2804:14d:1:0:181:213:132:2/.3` no **RA (RDNSS)**, não só no DHCPv6; Windows/celulares preferem o IPv6 → num site com 194 domínios só 1 consulta chegou ao Pi-hole. Testado e **revertido**: desligar o servidor DHCPv6 (`ativar`) tira o endereço DHCPv6 mas o DNS da Claro continua (vem no RA) — **confirmado com `rdisc6 -1 end0` na box**: com DHCPv6 desligado o RA muda os flags para `Stateful ... No` mas segue com `Recursive DNS server 2804:14d:1:0:181:213:132:2/.3` (lifetime 1800 s); reiniciar o modem não muda isso. Filtragem por IP do roteador só filtra **origem** (não dá para bloquear o DNS da Claro como destino); firewall IPv6 é só liga/desliga. DNS seguro (DoH) do Chrome **não** era a causa (teste com `--disable-features=DnsOverHttps` igual). Soluções reais: Tailscale DNS ligado nos aparelhos do Pedro (força tudo pelo Pi-hole), DNS IPv6 manual por PC, ou roteador próprio com o modem em bridge.
- **Sem QoS/SQM** (Opções Avançadas: só bloqueio WAN, passthroughs, gerência remota, multicast, UPnP). **Modo Bridged existe no painel** (`Configurações Básicas` → Tipo de Conexão WAN) → caminho para OPNsense/roteador próprio com SQM.
- Bufferbloat medido no PC (Ookla CLI): repouso 15 ms → baixando 93–125 ms (pior 444) → enviando 182–335 ms (pior 1.096). Download ~780 Mb/s, upload ~62–71 Mb/s. Script: `scratchpad/teste-rede.ps1 -Rotulo x`.

## Atualizações automáticas
- Sistema: `unattended-upgrades` com `origin=*`, blacklist `linux-u-boot-/linux-image-/linux-dtb-`, reboot automático **04:00** só se necessário.
- **Kernel, dtb e u-boot em `apt-mark hold`** de propósito: o boot depende das overlays `led-conf7`/`ddr3-660`/`ramoops`, do `rk3228_dmc` e do HDMI forçado; o Armbian não guarda o kernel anterior; e u-boot novo trava algumas RK3228A. Atualizar só **manualmente**: backup de `/boot` → `apt-mark unhold linux-image-current-rockchip linux-dtb-current-rockchip` → upgrade → reboot → conferir HDMI, `ddr-turbo status`, Pi-hole → se falhar, restaurar `/boot`. u-boot continua travado.
- Listas do Pi-hole: **todo dia 04:40** (`/etc/cron.d/pihole-listas-diarias`; separado do `/etc/cron.d/pihole`, que o `pihole -up` reescreve).
- Programa Pi-hole: **todo dia 05:10** (era domingo até 20/10) (`/usr/local/sbin/pihole-atualiza.sh`: `pihole -up`, confere se resolve e bloqueia, reinicia o FTL se não; log `/var/log/pihole/atualizacao-semanal.log`, syslog `pihole-atualiza`).
- Tailscale vem do repositório apt dele → entra no unattended.
- **Achado 20/10: o unattended NUNCA rodou sozinho.** `/etc/apt/apt.conf.d/02-armbian-periodic` traz `APT::Periodic::Enable "0"`: os timers `apt-daily*` disparam todo dia, mas o `apt.systemd.daily` sai na hora (último `unattended-upgrades.log` = 14/10, o teste manual). Corrigido em 20/10: `APT::Periodic::Enable "1";` no `52unattended-mopar` (carrega depois do 02). Conferir com `apt-config dump | grep Periodic::Enable` e se o `unattended-upgrades.log` ganha data nova no dia seguinte.
- **Confirmado 21/10:** com o `Periodic::Enable "1"`, o `apt-daily-upgrade` das 06:17 instalou sozinho `base-files`, `armbian-bsp-cli`, `armbian-firmware` e `armbian-config` (trunk.93 → trunk.104) em 8 min, "All upgrades installed", sem `reboot-required`; kernel/dtb/u-boot seguiram em hold (trunk.83, há trunk.104 disponível para a atualização manual). Conferir de manhã com `tail /var/log/unattended-upgrades/unattended-upgrades.log` e `grep upgrade /var/log/dpkg.log | tail`.
- **Achado 20/10: atualização semanal do Pi-hole perde a semana se a rede cair no domingo.** Em 18/10 o link `end0` estava caído (17/10 15:06 → 19/10 12:59) e o `pihole -up` falhou com "Failed to connect to github.com"; só tentaria de novo no domingo seguinte. Corrigido em 20/10: cron diário (o `pihole -up` não faz nada quando já está em dia). Pi-hole atualizado na mão para Core 6.5 / FTL 6.8 / Web 6.6.1.
- **Achado 20/10: espelhos do repositório beta do Armbian podem ficar quase parados** (redirector manda para `armbian.lv.auroradev.org`, 28 KB/s; `netcup-01` 1,6 KB/s; o PC também recebia 0), enquanto o Debian dava 9 MB/s na box. O `unattended-upgrade` fica preso baixando o `armbian-firmware` (164 MB) e segura o lock do dpkg, o que faz o `pihole -up` falhar em "Installing Pi-hole dependency package". Como aplicar: medir com `curl -w %{speed_download}` antes de culpar a box; se for o espelho, matar o `unattended-upgrade` (só se não houver `dpkg` rodando), instalar o resto com `apt-get install --only-upgrade <pacotes>` e deixar o Armbian para a rodada noturna.
- **"The versions file is incomplete" no rodapé do Pi-hole**: o `@reboot ... updatechecker` do `/etc/cron.d/pihole` roda antes da rede/DNS/relógio no boot e grava `GITHUB_*=null` em `/etc/pihole/versions`. Correção pontual: `sudo pihole updatechecker`. Permanente: `/etc/cron.d/pihole-updatechecker-boot` repete 5 min após o boot (14/10).

## DDR 660 MHz permanente (`ddr-turbo`)
- `blacklist rk3228_dmc` (também no initramfs: `update-initramfs -u`, o hook `99-uboot` refaz o `uInitrd`) + overlay `ddr3-660`. Sem o driver a box sempre sobe em 330.
- Serviço `ddr-turbo` (`/usr/local/sbin/ddr-turbo`) carrega o driver e fixa 660 (governor `userspace`). Marcadores em `/var/lib/ddr-turbo/`: `em-uso` (apagado no desligamento limpo) e `confirmado` (timer `ddr-turbo-confirma`, 10 min após o boot).
- Queda sem aviso **antes** de confirmar → desarma e fica em 330 (os 660 não aguentaram). Queda **depois** de confirmar (luz/tomada) → mantém 660. Os dois caminhos testados com `sysrq-c`.
- Comandos: `ddr-turbo status | armar 660 | desarmar`. Após desarme automático: investigar (`diagnostico`) antes de `ddr-turbo armar 660` + reboot limpo.
- Os 660 MHz que o devfreq informa aparecem como "600" na leitura do PLL feita pelo script (a DDR passa a usar outro PLL); o número que vale é o do devfreq.

## Proteções e diagnóstico
- **Watchdog**: systemd `RuntimeWatchdogSec=15s` (hardware dw_wdt, 28 s). Não age se a placa perder energia.
- **ramoops**: user overlay `ramoops.dtbo` (1 MB em `0x9ff00000`); `systemd-pstore` salva o dump em `/var/lib/systemd/pstore/` no boot seguinte. Dumps já analisados ficam em `/var/lib/blackbox/<evento>/`.
- `kernel.panic=10`, `panic_on_oops=1`, `hung_task_panic=1` (`/etc/sysctl.d/90-blackbox.conf`). Sem isso o kernel do Armbian (`PANIC_TIMEOUT=0`) fica travado para sempre após pânico.
- Journal **persistente no eMMC** (ramlog do Armbian desligado; antes os logs morriam na RAM a cada travamento).
- **`blackbox`**: a cada 30 s grava em `/var/lib/blackbox/AAAA-MM-DD.log` temperatura, CPU, memória, fila do eMMC, erros e MAC da rede, latência do DNS, processos em estado D.
- **`sudo diagnostico`**: junta boots recentes, dumps de pânico pendentes, caixa-preta antes do último boot e o fim do kernel do boot anterior. Primeira coisa a rodar depois de qualquer queda.
- Teste de exaustão: `/opt/netlab/stress.sh <min> <rotulo>` (stress-ng `--verify` + memtester + downloads da internet com hash + servidor HTTP do blob na porta 8099) e, do PC, um laço baixando `http://192.168.0.4:8099/blob` e comparando com `blob.sha`. Nada é gravado em disco (o blob fica em `/run`).
- **Não usar `speedtest-cli`** como teste de rotina (estava rodando no primeiro travamento).
